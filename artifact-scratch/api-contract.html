Kitchen Display System — API Contract

This is an implementation spec for the engineer building the backend, written directly off the working mock at src/api/mocks/handlers.js and fixtures.js. It is not product documentation — it exists so that once the real API returns exactly these shapes and status codes, the frontend's cutover is two environment variables and nothing else.

01

Auth

MUST Custom JWT, not Odoo's session cookie — chosen for a cross-origin SPA. REF The mock issues debug tokens (base64 of {type, userId, exp}, unsigned) with a 60s access TTL and a 24h refresh TTL, purely to exercise the refresh flow during local dev — issue real signed JWTs with whatever TTL you choose (15 min access is a reasonable default); only the response envelope below is contractual.

POST/auth/login
no auth

MUST Request body: { email: string, password: string }.

  1. Compare credentials. Match → 200 with the body below.
  2. No match (either field) → 401, code invalid_credentials. MUST the message must not reveal which field was wrong.
200 response 
{
  "access_token": "...",
  "refresh_token": "...",
  "expires_in": 900,                 // seconds
  "user": { "id": "u1", "email": "staff@kawahputih.test", "name": "Kawah Putih Staff" }
}

MUST A 401 here is terminal — the frontend calls this with retryOn401: false and does not attempt a silent refresh on it.

POST/auth/refresh
no auth

MUST Body { refresh_token: string } → same AuthResponse envelope as login on 200. Invalid or expired → 401, code invalid_refresh_token.

MUST On 401 from this endpoint, the frontend signs the user out client-side (clears tokens, redirects to login) — it does not retry again.

Dedup note (frontend behavior, no backend action needed): apiFetch in src/api/client.js dedupes concurrent refreshes — if 5 requests 401 at once, only one /auth/refresh call fires and the other 4 await the same in-flight promise. Your endpoint just needs to be safely callable more than once with the same token without side effects beyond issuing a new pair.

POST/auth/logout
bearer

MUST Body { refresh_token: string } → revoke it, respond 204 with an empty body. The frontend calls this with retryOn401: false too and ignores the response either way (it clears local state regardless).

Every endpoint below marked bearer must reject like this

MUST — this is the exact branch the mock's requireAuth() runs before doing anything else:

1. Read the Authorization header. Missing            → 401 unauthorized
2. Strip a leading "Bearer " (case-insensitive)
3. Token doesn't decode, or type !== "access"       → 401 unauthorized
4. Token expired                                     → 401 unauthorized
// only if all four pass does the handler run its own logic

Code for every case above is unauthorized, message "Missing or expired access token." — REF wording, MUST status 401 + the error envelope shape, since a 401 is what triggers the frontend's silent-refresh-and-retry-once.

Companies

GET/companies
bearer

MUST Returns Company[] filtered to the authenticated user (the mock does mockCompanies.filter(c => mockUser.company_ids.has(c.id)) — yours filters by res.users.company_ids).

200 response 
[ { "id": "c1", "name": "Kawah Putih", "logo_url": "" } ]
The frontend's ACL depends entirely on this endpoint being honest: the Config screen's company picker only ever shows what this call returns — it does no independent permission check. That means every other endpoint below that takes a company_id MUST re-verify server-side that the id belongs to the caller, exactly as if a client sent an id from this list belonging to someone else.

04

Order lines

Kitchen state lives on sale.order.line, not sale.order — one order can have lines in different columns at once. Each line's table_number is its parent order's existing client_order_ref.

GET/order-lines
bearer

MUST Query params: company_id (required string), since (optional ISO-8601 datetime). This is the literal mock logic:

orders = allOrders.filter(o => o.company_id === company_id)
cards  = orders.flatMap(order => order.lines.map(line => flatten(order, line)))
if (since) cards = cards.filter(c => c.updated_at > since)   // strict greater-than, not >=
return 200, cards   // OrderLineCard[] — see Shapes
Not enforced by the mock — you must add it: the mock trusts company_id as given, with no check that it's one of the caller's allowed companies. That's acceptable in a browser-only mock; it is not acceptable in the real backend — see the Companies section above.

REF "Open" is undefined in the mock — it returns every line regardless of the parent order's own Odoo state. Decide your own open/closed filter; the frontend renders whatever comes back with no client-side filtering.

PATCH/order-lines/{lineId}/state
bearer

MUST Body { kitchen_state: string }. Exact validation order in the mock:

  1. Auth check (see Auth section) → 401 unauthorized
  2. Line lookup by lineId across all orders. Not found → 404 not_found
  3. Read kitchen_state from the body — the mock never validates it's one of the 4 enum values, it's written through as-is
  4. One hardcoded rule: current state is served and requested state is pending → 409 invalid_transition. Every other combination, including nonsense values, is accepted and written
  5. Otherwise: write kitchen_state, stamp updated_at = now, respond 200 with the updated OrderLineCard
Not enforced by the mock — you must add it: (a) that kitchen_state is actually one of pending | cooking | ready | served, and (b) the real transition rules signed off with product — served → pending is a placeholder demo rule, not a spec. MUST whatever rules you land on, an invalid transition returns 409 with the standard error envelope — the frontend already rolls the card back and shows a toast on any 409 here, no code change needed on the frontend side no matter which transitions you block.

MUST On success, also broadcast order_line.updated over the WebSocket (see below) with the same updated card — the frontend's board updates instantly from the socket in other open tabs/devices, not from this response alone.

06

WebSocket gateway

Odoo 18 has no native WebSocket (it speaks bus.bus long-polling) — this is new infrastructure, not a mock-to-real swap like the REST endpoints above.

wss://{ws-host}/ws?company_id={companyId}&token={accessToken}

MUST Same JWT access token as REST. Token invalid/expired at connect time → close with code 4401.

What the frontend actually does with 4401 today: kitchenSocket.js checks for close code 4401 and fires an internal __token_expired__ event, but useKitchenSocket.js doesn't currently act on it — the socket just falls into its normal exponential-backoff reconnect and re-reads whatever access token is in memory at that moment (which is usually already fresh, since REST calls silently refresh it independently). Don't build gateway-side logic assuming an immediate refresh round-trip follows a 4401 — there isn't one yet.
TypeDataWhen
order_line.createdOrderLineCarda new line enters the company scope
order_line.updatedOrderLineCardkitchen_state or any displayed field changes
order_line.removed{ id }a line leaves the scope
ping{ ts }heartbeat every 25s — client never replies

MUST Message envelope is always { "type": string, "data": ... } — the frontend does JSON.parse(event.data) and silently drops any frame that fails to parse or has no matching type.

Reconnection the gateway should expect

Client backoff: 1s → 2s → 4s → 8s → 16s, capped at 30s, ±20% jitter. After 3 failed attempts it switches to polling GET /order-lines?...&since=<last_updated_at> every 5s while still retrying the socket. On any successful reconnect it fires one reconciliation GET before trusting the socket again — so the gateway can be simple and stateless per connection; missed events are always backfilled by that REST call, not replayed by the socket.

07

Gaps between the mock and a real backend

Everything above is either already true of the mock (and just needs re-implementing faithfully) or explicitly flagged where the mock cuts a corner a real backend can't. This is that second list, gathered in one place:

  • 1
    kitchen_state field on sale.order.line
    Doesn't exist in stock Odoo 18 — new selection field, values pending | cooking | ready | served, default pending. Small addon.
  • 2
    Company ACL on every company_id-scoped call
    The mock trusts the param outright. Real backend re-checks res.users.company_ids server-side every time — see Companies and Order Lines above.
  • 3
    kitchen_state enum validation on PATCH
    The mock writes whatever string it's given. Reject anything outside the 4 valid values.
  • 4
    Real transition rules
    The mock's served → pending block is a placeholder to prove the 409/rollback path works — get the actual rule set signed off with product.
  • 5
    Definition of "open"
    GET /order-lines has no filter in the mock at all. Decide what counts as open for kitchen purposes.
  • 6
    Real JWT issuance
    The mock's tokens are unsigned base64 JSON, readable and forgeable by design (it's client-side JS). Issue real signed tokens; keep the same response envelope.
  • 7
    WebSocket gateway itself
    Doesn't exist anywhere in the mock as real infrastructure — wsMock.js only fakes the client-visible contract. Build the bridge from Odoo's bus (or direct model writes) to the event contract above.
