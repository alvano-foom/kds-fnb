# Business Rules

- **Multi-tenant**: one Odoo company = one outlet/tenant. A user may belong to several companies; the KDS only ever shows companies the logged-in user is assigned to in Odoo (`res.users.company_ids`), never all companies in the system.
- **Kitchen states**: `pending → cooking → ready → served`, stored in a new `kitchen_state` field on **`sale.order.line`** (not `sale.order`, and not one of Odoo's built-in order states, which track the sales/invoicing lifecycle, not kitchen prep). A single order can have lines in different kitchen states at once — the board's unit of work is the line.
- **Table tagging**: each line's card shows a table number, read from its parent order's existing `client_order_ref` field (labeled "Customer Reference" in the Odoo quotation form) — no new field needed for this.
- **State transitions**: the frontend allows dropping a card on any of the 4 columns; the backend is the enforcement point for any transition rule (e.g. the mock blocks `served → pending` as a demonstration of the `409` + rollback path — confirm the real rule set with the product owner before backend implementation).
- **Scope of a kitchen display**: one device is normally fixed to one company for a whole shift (Point of Sale scoping was removed — company is the only scope); configuration is saved locally and doesn't need to be re-entered on reload.
- **Branding**: outlet name and logo are configurable via `/tenant/config`, never hardcoded — default sample name is "FOOM Outlet". Brand color (primary + secondary) is **not** part of the API at all: it's a frontend-only setting picked via color inputs on the Config screen and persisted to the browser's `localStorage`, exactly like a light/dark theme preference. Default sample colors are purple (`#9333ea`) primary and orange (`#f97316`) secondary, used only until the browser's saved choice hydrates.
- **Reference UI**: existing Bahasa Indonesia product screens (outlet header with logo, "Company"/"Point Of Sale" config screen, 4-column board labeled Pesanan Masuk / Diproses / Siap Diantar / Selesai) are the design baseline for this rebuild — see `.spec/features/kitchen-display-system/requirements.md` for the source screenshots' context.
